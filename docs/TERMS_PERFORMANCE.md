状态：现行参考（2026-10-02；第 7 节 2026-11-18；第 6 节 2026-11-13；第 2 节 2026-11-12）。两轮优化都已合入 main；逐任务的过程记录和原始样本已删除，见开源前私有历史中的 `docs/TERMS_PERFORMANCE_TASKS.md`、`docs/TERMS_CHARACTERS_PERFORMANCE.md` 和 `docs/acceptance/terms-*`。没做完的方向在 issue #1。

## 2. 常驻核心进程

原生宿主在进程内直接调用核心，角色命令不再经子进程。`illustash-terms serve`（`native/terms/src/service.rs`）保留为父进程私有的逐行 JSON 通道，供测试（`native/terms/tests/baseline.rs`、`tests/test_terms_service.py`）和外部调用方使用：

- 经私有 stdin / stdout 管道，不开端口；命令顺序执行。
- 与单次 CLI 共用同一套事务函数（`app_service::character_request`）：一个命令一个事务，失败整事务回滚，名字、历史和后台事件仍在同一事务里；跨进程由 SQLite `BEGIN IMMEDIATE` 仲裁。
- 每条命令独立打开并关闭 SQLite 连接，空闲时不占连接。
- 业务拒绝不退出；stdin 关闭即退出，崩溃由调用方在下次请求时重启，不自动重放。

## 3. 其他保留下来的做法

- 全量 refresh：核心先按原内容指纹预检 WD，只有真正变化的图继续走证据包路径；实体树与链接镜像的 UPSERT 值相同时不重复 UPDATE；全量归属在同一事务里只物化一次规则结果。
- 图片 NSFW 查询：需要总数的请求在同一读事务里物化一次筛选结果，再计数和分页；例外是只隐藏 NSFW、按日期排序且不带其他筛选的图库页（#48）：先用两次索引计数估算隐藏后剩下的比例，剩下至少 70% 且页面不超过前一半时，直接按 `assets_date` 索引分页、另行计数；NSFW 占多数或翻得更深时回到物化。阈值依据是 10k/50k 合成库按 NSFW 占比扫描的交叉点（约 40%），其余形状物化更快。同时筛标签与「仅 NSFW」时由 NSFW 投影驱动。没有持久缓存，没有跨请求复用。
- 角色命令的预演跳过末尾的派生表刷新，真正的刷新在核心里做。

## 4. 底线

以后再做性能优化，仍然是这几条：用户看得到的结果不变；对照零差异，比较器不放宽；对照基准（#201，`native/terms/tests/fixtures/baseline/`）不重录；不碰真实图库，要用就按「每步单独授权、只读一致性副本」的约定；回退一直可能。

## 5. 固定原生宿主基准

`tools/bench_native_contracts.sh /absolute/release/contracts-executable /absolute/main-host /absolute/candidate-host` 固定对两个显式 release 二进制交错运行各三次，分别取三次独立进程的中位数；测试入口用 `cargo test --release --locked --manifest-path native/terms/Cargo.toml --test contracts --no-run` 构建，debug 入口拒绝测量。main 二进制须从记录的远端 main 提交用 `cargo build --release --locked` 构建并单独保存，不能使用候选替代；脚本不读取用户包，全部输入由本仓库 HTTP 合成契约恢复至新临时目录。

数据集固定为 4,096 张合成资产、2 个参考角色：保留夹具中 3 图的证据与裁决，其余 4,093 图按固定编号/尺寸/日期加入 source 与应用表且未分类，不读取或解码图片。

计时前一次性重建和扩容合成包，用显式基线宿主的 `migrate --db` 迁移到它要求的版本。两个宿主都以普通模式打开，遇到版本不兼容时基准失败。每轮复制同一份已准备的输入，含物理上独立、图库 ID 相同的切换目标。开库取 7 次宿主启动到 bootstrap 就绪的中位数，切库取 20 次切换到 bootstrap 就绪的中位数（第一次切换预热）。SQL 恢复、扩容、迁移和复制均发生在计时前。

浏览分页 `limit=100&offset=2000`、计数、单图详情各预热 5 次后测 50 次，标签加到 a/b 两图与撤销各测 20 次；每轮取平均请求时间（包含 loopback HTTP、JSON 解析及核心执行），最后取三轮平均值的中位数。内存为 `wait4` 返回的宿主整个生命周期峰值 RSS，macOS 以字节、Linux 以 KiB 转成 MiB（1,048,576 字节），不含测试进程；这是合成基础宿主口径，不覆盖大图库刷新、模型/worker 峰值或 Windows。

用户允许直接接受的门槛：候选内存增加严格小于 10 MiB，各项延迟退化严格小于 20%；脚本逐项打印 accepted/exceeds-threshold，超阈值以非零退出，零/负退化也接受。保持同数据、release、三次中位数，不以单次测量或 debug 数字替换。性能脚本不会更改任何契约期望或既有 golden。

2026-10-02，macOS arm64，实际 main `fc49031` release 对本变更候选 release，固定脚本各三次中位数：main 峰值 16.734 MiB，候选 16.813 MiB；浏览/计数/详情/标签/撤销的 main 基线分别 2.886/1.799/2.016/2.091/2.930 ms，候选分别 2.878/1.799/2.013/2.049/2.920 ms。最大延迟退化低于 +0.01%、内存增加 0.078 MiB，按上述用户阈值直接接受。基准仅回收本轮创建的宿主，wait4 回收后停止重复清理，不按端口查找或终止其他进程。该结果只说明此固定合成基础宿主样本，不代表四类契约的全部操作或整个 Python 行为网的性能。

## 6. 整应用识别吞吐基准

`tools/bench_recognition.py`（用法见文件开头）测一批新图从扫描到识别、导入完成的总时间、各阶段占比和峰值内存（#213 第 1 步）。后续识别性能改动使用这份基准对比，按 [AGENTS.md](../AGENTS.md) 经 `collab_run.py timing` 等待 heavy、vm 槽空闲且开跑前 30 秒 CPU 平均占用不超过 20%，再独占两个槽运行；记录负载与虚拟机状态。

**样本**：同一种子生成的 200 张合成图（8 种常见插画尺寸循环，750×1334 到 2480×3508，JPEG 与 PNG 混合，共 538 MP、207 MiB）和 2,000 个合成角色各一条随机锚点。不是真实图库，也不说明识别准确率。

**端到端**：重定位布局（与 `tests.platform_recognition_models` 相同）里启动 release 宿主，folder 来源新建图库后 `POST /api/sync`，每 50 ms 轮询到完成。宿主照常拉起 `illustash-recognition`，每 25 张一批，边识别边导入。不开名字、索引检查和研究任务，所以不含导入之后的相似计算等后台任务。线程数是产品默认值；下表和 Windows 的数字都是 CPU 执行后端，平台加速后端的对比见本节后半：WD 在 Windows 上用 ONNX Runtime 默认值（每个物理核一个 intra-op 线程，2026-10-21 起，#213），macOS 用 4 个；CCIP 两边都用 ONNX Runtime 默认值。下表 2026-10-19 的数字是改之前测的，当时两边 WD 都是 4 个线程。图片文件已在系统缓存里。

**阶段分解**：`recognition-compute` 示例的 `bench-stages` 在一个进程里按 worker 的顺序处理同一批图并逐步计时。计时用的 WD 会话第一张图与生产 `ModelSessions` 逐位比对，配置变了基准就报错，不会悄悄测成别的东西。

- 解码：读文件并解码成 RGB。
- WD：预处理（缩放到 448）加推理。
- CCIP：预处理加推理。
- 检测与分级：WD 概率转标签和分级，加角色锚点认领。现在不另跑检测模型。
- 写结果包：每批的 npy、标签、sidecar 和完成标记。
- 写库：端到端里宿主在识别阶段用掉的 CPU 时间除以张数，包括导入校验、写 source / 应用库和投影。状态轮询的开销在同步完成后按同样频率空轮询量出来，已经扣掉。

worker 本身是串行的；导入在宿主进程里和下一批的识别同时进行，所以写库主要占 CPU，不直接加到墙钟上。占比按各阶段每张耗时之和计算。

**峰值内存**：每 20 ms 采样宿主和 worker 各自生命周期的峰值。macOS 是 `phys_footprint`（活动监视器「内存」一栏的口径），Windows 是 `PeakWorkingSetSize`。两边口径不同，不能直接比。

2026-10-19 的结果（Windows 在 `7a78509`、macOS 在 `501e475` 上测，两者之间只改了测量条件的记录；ONNX Runtime 1.30.0 CPU，两边模型文件相同；各 3 次中位数）：

两个平台上 WD 和 CCIP 两个模型的推理合计都占九成左右；解码、认领和写包加起来不到 3%。要提速，先看模型推理（执行后端、线程数），不是 I/O 或写库。写库主要和下一批的识别同时进行，墙钟上只多出最后一批的收尾导入。

这台 M2 比 Windows 机器慢：WD 每张多约 50%，CCIP 多到约 2.6 倍。第 1 步推测 CCIP 的默认线程数在 M2 上把能效核也算进去而吃亏；#213 第 2 步在空闲的 M2 上做了模型级对比，CCIP 限 4 线程和默认值一样快，WD 改 8 线程反而慢约 10%，推测不成立。同一次对比里，这台 M2 空闲时的 WD、CCIP 推理只有上表阶段耗时的一半左右，说明上表的 macOS 数字受了测量时负载的影响。

**Windows 的 WD 线程数（2026-10-21，#213 第 2 步）**：同一台 Windows 机器、同样 200 张合成图，在同一时段与 WD 4 线程交替各测 3 次，WD 8 线程（等于这台 8 核机器上的 ONNX Runtime 默认值）每张 897 ms（三次 897 / 905 / 897），4 线程 1,116 ms，快约 20%；WD 阶段 818 → 623 ms，worker 的 CPU 时间多约 30%。12 线程 830 ms、16 线程 920 ms（另测，16 线程和宿主导入抢核），没有采用。产品改成不设线程数（用 ONNX Runtime 默认值）后，在同一台机器上用 100 张合成图把 main、新默认值和显式 8 线程交替各测 3 次：每张 1,139 / 923 / 926 ms，新默认值与显式 8 线程相同，比 main 快 19%。CPU 执行后端的输出与线程数无关，逐位相同，所以这个改动不影响识别结果、固定期望和 `tests.platform_recognition_models` 的逐位比对。执行后端（CoreML、DirectML）的评估结论见 [#213 的评论](https://github.com/shio-vinyl/illustash/issues/213)。

以上 2026-10 的 Windows 测量三次总时间相差不到 3%，阶段耗时相差不到 1%，可以直接拿来对比。macOS 三次的阶段耗时相差约 ±10%，第一次总时间明显偏高（开始时前一个 heavy 作业的余下负载还没退），所以 macOS 上比较改动前后时，要在同一时段交替测，差距小于 10% 不能下结论。每次 `GET /api/sync` 约花宿主 3 ms（Windows）到 6 ms（macOS）CPU。这些数字只适用于这组合成样本和这两台机器。

**macOS 的 WD 也走 Core ML（2026-11-13，#375）**：Apple M2 8 核、16 GiB、macOS 26.7.1、ONNX Runtime 1.30.0，接电源、低电量模式关闭、无虚拟机；经 `collab_run.py timing` 在开跑前 30 秒 CPU 平均占用 13.4% 时独占 heavy 与 vm 槽。正式实现 `d8633ad2` 的同一组 release 二进制和原始模型，仅切换 WD 后端，两组 CCIP 均用 Core ML；同样 200 张合成图，各交替三轮。端到端中位数由 207.5 s 降至 71.5 s（吞吐约 2.90 倍、耗时减少 65.6%），WD 含预处理由每张 758.4 ms 降至 177.5 ms（约 4.27 倍），worker CPU 时间由 665.7 s 降至 31.2 s。端到端各轮为基线 207.5 / 291.1 / 193.2 s、双 Core ML 71.5 / 80.1 / 67.9 s，仍有明显波动；数字只适用于本机和该合成样本，不代表识别准确率或其他芯片，详细验收见 [PR #377](https://github.com/shio-vinyl/illustash/pull/377)。

代价是额外约 446 MiB 的 WD 执行文件、约 892 MiB 的 WD 编译缓存，以及 worker 峰值内存中位数由 1,421 MiB 升至 1,514 MiB（增加约 92 MiB）。首轮应用编译缓存为空时，启动 worker 到第一张由 10.6 s 增至 18.8 s；其后两轮复用缓存时由 4.54–4.57 s 增至 9.15–9.75 s，因此批量吞吐收益不能直接当成单张启动收益。两组各六次端到端/阶段运行中的缓存大小保持不变，独立实际模型验收还核对了热启动前后缓存文件的 inode、mtime 和大小；WD 与 CCIP 的缓存分别保留。变体缺失、损坏或加速失败时仍可用原始模型 CPU，模型身份与回退规则见 [安装与平台](BACKEND_TASKS.md#识别的执行后端)。

## 7. 10 万与 50 万张已识别图库

夹具为每张图生成 1 条分级、4 个通用标签、1 条角色识别结果，通用标签从固定的 256 个 WD 词中分配。两档分别有 2,000 和 10,000 个角色，每张图归属一个角色，每 10 张有 1 张人工确认收藏。源库保存识别行，应用库保存对应的浏览数据和上次同步的指纹。数据源是合成的 Photos SQLite 元数据，计时不涉及图片解码、模型推理或网络服务。

### 普通图库分页与计数

普通图库计数直接取资产总数，再按排除表和副本表查找仍在库的排除、折叠图片并扣减。两张表都记录的 UUID 只扣一次。分页继续按同一读事务的可见性、筛选和排序取行并补充当前页字段。`count=0` 跳过总数，响应中的 `total` 为 `null`。

补充用户标签时，先查出当前页的核心资产 ID，再按这些 ID 读取有效裁决。SQLite 可以在运行裁决的窗口函数之前使用 `term_verdicts_image` 索引，只处理当前页的分区。按裁决查资产主键，避免查询从全库资产出发。页内查询与 `asset_tags` 视图共用标签投影，按同一裁决规则处理标签清除和撤销。

2026-11-21 在同一台 Windows 11 x64 验收机（build 26200，i7-11800H，32 GiB 内存，Rust 1.99.0）对比 release `f2881f38` 与 `4595258e`。每档共用一份合成图库，独占 Windows 窗口，开跑前 30 秒采样的平均 CPU 占用分别为 1.43% 和 1.27%。每个请求先预热一次，再取 10 次回环 HTTP 请求的均值，包含 JSON 解析。分页每次取 100 张，偏移 2,000。

| HTTP 请求（ms） | 10 万张基线 | 10 万张候选 | 50 万张基线 | 50 万张候选 |
|---|---:|---:|---:|---:|
| 普通图库计数 | 20.991 | 4.529 | 85.949 | 13.163 |
| 分页，含总数 | 42.798 | 10.519 | 188.005 | 19.968 |
| 分页，`count=0` | 26.080 | 8.367 | 128.714 | 10.939 |

两档的普通计数、分页与标签筛选的完整响应一致。2,100 张的最小夹具也通过，标签筛选页按偏移之后实际剩余的匹配数校验，并用来源标签行核对顺序、UUID 和收藏字段。

阶段耗时来自同机的临时插桩 release 宿主，各取预热后 10 次的均值。端到端表使用未插桩宿主。分段值来自各自的请求轮次，直接比较同一阶段的前后耗时。

### 原规模基准（#458）

开库从启动原生 HTTP 宿主测到收到 bootstrap 响应，关闭自动同步、名字和索引等后台任务。图库页每次取 100 张，从偏移 2,000 开始。四项读取各先预热一次，再取连续 10 次回环 HTTP 请求的均值，包含 JSON 解析。撤销通过 HTTP 撤回刚刚确认的一张收藏，并核对撤销后的状态。名字投影和两种同步各启动一次 release CLI，计入进程启动开销。先测原库，再向来源增加 8 张已有分级结果的图片。两次同步分别核对发现、导入为 0 / 8，移除与待识别均为 0。夹具构造不计时，保留操作系统文件缓存。

2026-11-18，Windows 11 x64（build 26200），Intel Core i7-11800H（8 核 16 线程）、32 GB 内存，Rust 1.99.0，release 提交 `68d74c90`。两档各运行一轮，经 `collab_run.py timing --slot windows --exclusive` 独占远程验收机。30 秒平均 CPU 占用直接采自执行测量的 Windows，两档开跑前分别为 1.99% 和 1.96%。开库、同步、名字投影和撤销为单次观察，读接口为每次请求均值。

| 操作 | 10 万张 | 50 万张 |
|---|---:|---:|
| 开库到 bootstrap（ms） | 56.13 | 131.35 |
| 无变化同步（s） | 10.92 | 55.58 |
| 新增 8 张的同步（s） | 10.90 | 55.90 |
| 全库名字投影（ms） | 35.88 | 94.10 |
| 撤销单张收藏（ms） | 16.37 | 11.63 |
| 普通图库页，含总数（ms） | 41.77 | 189.39 |
| 无筛选计数（ms） | 20.60 | 107.84 |
| 单图详情（ms） | 5.55 | 6.55 |
| 按单个通用标签筛选计数（ms） | 11.33 | 50.63 |

图库规模增加到 5 倍，零变化同步耗时从 10.92 秒增至 55.58 秒；新增 8 张与零变化分别相差不到 0.02 秒和 0.32 秒。同步各阶段的耗时尚未拆分，见 [#627](https://github.com/shio-vinyl/illustash/issues/627)。50 万张时，每页取 100 张并返回总数平均用时 189.39 ms，单独取总数平均用时 107.84 ms，查询拆分与优化见 [#626](https://github.com/shio-vinyl/illustash/issues/626)。
