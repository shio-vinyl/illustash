# 待办清单（讨论过、还没做的）

整理于 2026-09-25，2026-09-28 更新后端交付状态（应用 schema 36）。已完成功能的做法见 [WEB_V2.md](WEB_V2.md)。

## 产品底线与已定的约束（新会话先读）

- **图片只留本地**：图片和从图片算出的特征都不发给任何大模型或多模态 API，也不用于训练。唯一例外是设置里一个**默认关闭**的「以图搜图」开关（见第 5 项）。
- 可以从外部**拉取**公开数据（Danbooru、Bangumi、角色索引）；发出去的只能是文本查询（tag 名、作品名、MD5）。纯文本的结构化或翻译可以接 DeepSeek 这类 API。
- 外网流量超过 500 MB 要先问用户。不硬编码猜测的标签名，要查 `tags/tags_v3.csv`。没看过图，不对画面内容下结论。
- **标记类操作一键完成**：不加弹窗，不设必填项，给自动默认值，缺的信息等真正要用时再补（例：原创角色）。
- Photos 只读；图库是索引，不删 Photos 里的图。大批量识别交给 Windows，少量增量在本机跑；每次启动时同步；只收录 X 和 Pixiv。

## 功能

1. **画廊式偶尔提问（主动学习）**（2026-09-26 **已上线**）
   - 挑图（`Store._question` / `ask_batch`）：先问「可能认错」（附「是 <对手>」按钮），再问人工确认不足 5 张的角色（单人图）；
     所有角色都够了以后，首页卡片改为随机抽查（`kind=sample`），给第 6 项校准攒无偏样本。排除的图、原创角色标记不问。
   - 位置：详情面板和大图顶部的提问条（Y / N 键）；首页第一个日期组后的「认一认」卡片（同一角色最多 6 张，点掉不是的，再点「都对」或「其余 N 张是」）。
   - 频率：浏览页至多每 4 张问一次，连续 3 次不理会，本次访问就不再问；整理页（角色页、未识别等）不节流。「显示」里可以关掉。
   - 记录：新表 `asked`（schema 30），问过的不再问；「以后再说」让该角色歇 7 天；`action_id` 关联撤销步骤，校准时要排除已撤销的回答。
   - 实测（库副本）：一张卡片让一个角色从 2 张确认变成 6 张，学习线程学出原型，新认领 28 张。
   - 数据背景：两千多个有机器识别的角色一张人工确认都没有，只有几十个角色有原型——答案优先用于这些角色。
   - 之后另一个会话加了：随机抽查（`asked.kind='audit'`，侧栏「整理 › 随机抽查」）、优先问学习线索（`kind='hint'`）。
   - 截至 2026-09-27 的回答：抽查 228 是 / 43 不是，线索 107 / 20，攒种子 166 / 13，可能认错 0 / 3。
   - 还可以做：按回答率调整节流；「认一认」卡片里长按看大图。

## 移动端与桌面端（2026-09-26 定方向，移动端阶段再做）

- **受众**：国内安卓用户多数不开云相册，图只存在手机本地；X、Pixiv 各自保存到自己的文件夹，来源按文件夹判断。
- **远程算力必做**：安卓的首次全量由手机经局域网把缩略图（约 448 px）传给桌面端，桌面端算完把结果传回。5 万张约 2–3 GB（估算）。
  - 桌面端必须支持 **Windows**；
  - 配对用扫码，不需要账号或服务器；
  - 国产 ROM 会杀后台：首次全量做成带常驻通知的前台任务，提示保持亮屏或插电。
- **iOS（开了 iCloud 照片）**：桌面端直接读 Mac 上本机的 Photos，两端之间只同步识别结果和人工结论（走用户自己的 iCloud 私有数据库），不传图片。
- **分工**：首次全量和大规模重算交给桌面端；日常增量尽量在手机本机跑，桌面端是加速器，不是必需品。
  低端安卓机跑不动时，增量也交给桌面端。
- **资产 ID 链接化（做移动端之前必须完成）**：现在人工结论按 Mac Photos 的 UUID 存（`tests/reference/web/store.py（#9 已删除）` 的 `assets.uuid`），
  跨设备对不上；安卓 MediaStore ID 在重新扫描后也可能变。改成**内部资产 ID + 设备链接**
  （iOS `PHCloudIdentifier`、Mac Photos UUID、安卓路径加内容哈希），和身份模型「内部 ID + 外部 tag 链接」同一个思路。
- **待验证**：
  - iPhone 和中端安卓机跑 WD、CCIP 的实际速度；WD 约 450 MB，手机端可能要换小模型或按需下载；
  - `ZORIGINALSTABLEHASH` 在 Mac 和 iPhone 上是否一致；
  - iCloud「优化存储」开着时，Mac 上没有原图，桌面端要改读缩略图或先下载。

## Rust 迁移（2026-09-27 冻结）

**2026-09-27 后续讨论更新**：以 [架构演进与 Rust 改写方向](ARCHITECTURE_DIRECTION.md) 的边界、证据和恢复条件为准。按完整业务闭环迁移并调整架构；独立连接试点已完成，未合入 main，稳定应用全面迁移已于 2026-10-01 按架构文档的 M0–M5 批准；冻结分支仅作规格与对照。

以下保留冻结时的初始判断，其中“不会更快”“唯一可能带来性能收益”“瓶颈就在桥上”“方案 0 能让门禁变绿”均未经充分归因或验收，不能作为已证实结论。现有撤销分派只经过原单连接架构验证；多连接缓存失效、事务和回滚仍须验收。恢复无需等待所有溯源研究结束，先验证核心与研究边界，并明确独立交付排期。

- **现状**：Codex 在 `codex/rust-migration` 分支
  把第三阶段做到 ABI 21：图库查询、人工写入、完整撤销、身份图、名称、作品等已迁到 Rust，双后端 394 项测试和真实库副本逐表对照一致。
  **默认关闭**（`PI_RUST_CORE=1` 才启用），没有合进 main。说明在该分支的 `docs/RUST_CORE.md`、`docs/RUST_PHASE3_ACCEPTANCE.md`。
- **为什么冻结**：
  - 没有性能收益：macOS 页面查询 Python 89.7 ms，Rust 89.2 ms；
  - Windows CI 的「3000 实体搜索 < 300 ms」门禁连续失败（353–446 ms）；
  - 溯源还没闭环，现在迁移，数据模型一改就要在两种语言里各改一遍。
  这不是 loop 会话的上下文问题，是目标和架构的问题。
- **根因**：Rust 不自己持有数据库，每条 SQL 都通过回调交给 Python 的 SQLite 连接执行。这个架构下，Rust 只能做到和 Python 行为一致，
  不会更快，也不能脱离 Python 独立运行。
- **以后恢复时走方案 A**：让 Rust 自己持有 SQLite 连接（例如 rusqlite），事务也由 Rust 管理，Python 只作为研究/推理 worker。
  这是 Rust 独立运行、做 Windows 桌面端和「安卓借桌面算力」节点的前提，也是唯一可能带来性能收益的路。改动大，先出方案再动手。
  - **有利条件**：已迁移的 Rust 业务代码都通过 `dyn Database` 接口访问数据库，换成 rusqlite 实现后业务逻辑基本不用改。
  - **瓶颈在哪**：`web/native_core.py（#9 已删除）` 用 ctypes 回调，每条 SQL 都要走一轮「Rust 编码 JSON → Python 解码 → sqlite3 执行 → 编码结果行 → Rust 解析」。
    Windows CI 上同一个 3000 实体测试，默认 Python 模式通过、Rust 模式超时，说明代价就在这座桥上。
  - **三档方案**：
    - **方案 0，只修桥**：ctypes 换成 PyO3，JSON 换成二进制，多条 SQL 合并成一次回调。能让 Windows 门禁变绿，但仍离不开 Python，不作为方向。
    - **方案 1，Rust 持有连接**：Rust 用 rusqlite 自带的 SQLite 打开数据库，事务也由 Rust 管理；已迁移命令在 Rust 内部执行完所有 SQL，只跨语言返回一次结果。
      迁移期间未迁移的 Python 代码怎么访问数据库：
      - (a) 反转桥，Python 借 Rust 的连接：全程单连接，但要给 Store 写一层兼容 sqlite3 的适配，工作量大，最终架构里也用不上；
      - (b) **两个连接，按命令划分归属（推荐）**：库已经开了 WAL，由 SQLite 的锁排队写入；每个写命令只归一方所有，撤销这类跨边操作由 Rust 统一分派（已完成）；
        缓存失效靠数据库里的版本号和触发器，多个连接下照样有效。
    - **方案 2，最终形态**：Rust 进程提供 HTTP 服务和前端静态文件（以后可以套 Tauri，也可以作为局域网算力节点）；
      Python 只以子进程方式做推理和溯源研究，按第一阶段定好的 JSON 契约交回结果，由 Rust 导入，不直接写人工知识库。
      过渡时按路由逐个接管：Rust 在前面，未迁移的路由转发给 Python 服务，并如实记录哪些路由是真迁移、哪些只是转发。
  - **推荐路线**：方案 1(b) → 方案 2，跳过方案 0 和 1(a)。迁移的价值是能独立运行、方便跨平台交付，不是跑得更快；
    1(b) 的数据库访问层和命令归属，正好是方案 2 的地基。
  - **动手前先剖析**：在 Python 版本上先做一次性能剖析。页面查询约 89 ms，很可能大部分是 SQLite 本身的耗时，这部分换语言也快不了，改 SQL 或索引更有效。
  - **恢复时机**：溯源第一阶段验收完成、核心数据语义稳定，并且 Windows 桌面端或移动端交付正式排上日程。
  - **可以复用**：已迁移的业务逻辑、差分对照脚本（`tools/verify_rust_*.py`）和跨后端撤销测试；要重做的是数据库访问层和事务边界。
  - **恢复前先做**：整理 `RUST_CORE.md`（目前是只追加的流水账，末尾的「剩余工作」已经过时），清理 10:04 的遗留 stash，
    用 main 的最新 schema 重新合并。

## 已知的局限与可以改进的地方

- **相似检测**（`web/relate.py（#9 已删除）`、`web/similar.py（#9 已删除）`）：
  - 一张图多了个小插图、另一张那里是空白，会被判成「色块遮住」，归类不准，但分组是对的；
  - 布局相同的两张聊天截图会被判成差分；这类图大多已经被排除规则排除了；
  - 还不支持部分重叠，比如一张长图被拆成两张、两张之间有重叠的情况；
  - 除了纯色块和规则马赛克，打码和内容变化在像素上分不开，所以贴纸、涂改都归为差分；
  - 每对比较 0.5–0.75 秒；第一次全库扫描用了约 46 分钟，以后只处理新增的图。
- **相似分组的提示**：「外观相似：第 N 组」这类提示大约六成准，所以措辞比较弱。
- **双胞胎**：nozomi 和 hikari 几乎长得一样，CCIP 分不开，这是模型本身的局限。
- **产品化**：做成 app 之后，同步时机、Photos 权限等都要重新设计。现在还是 demo 阶段。
- **名字与身份的增量（#38）**：方案 A 已全部合入（#102–#105），名字和结构类提交、名字更新器、读侧都不再随图库规模整库载入。2026-10-15 用户决定不做方案 C（把权威迁到 `term_*`）。剩下两处仍随规模增长，暂不处理：
  - 名字更新器每个任务提交前的来源指纹核对（`app_names::scope`）整读 `entities` 和当前 `links`（50k 合成库约 24.5 MiB 堆峰值）；只在联网补名字时发生，耗时以网络为主。
  - `identity_policy = hybrid` 下每次决议、新建身份都整体重建身份图（50k 合成库每次约多 0.4 s）。
