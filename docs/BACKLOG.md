# 产品方向与约束

状态：现行参考，2026-11-21。这里只保留仍有效的产品方向与约束；现行界面见 [WEB_V2.md](WEB_V2.md)，具体任务与验收进度见 GitHub Issue 和里程碑（「现阶段路线」一节）。2026-10-06 以前的决定和编号来自开源前历史，引用规则见 [AGENTS.md](../AGENTS.md#公开库规则)。

## 产品底线与已定的约束（新会话先读）

- **图片只留本地**：图片和从图片算出的特征都不发给任何大模型或多模态 API，也不用于训练或改进任何共享的模型（包括本软件自带的识别模型）。唯一例外是设置里一个**默认关闭**的「以图搜图」开关（见第 5 项）。本软件会根据你的标注在本机学出一些只属于这个图库的打分规则（如角色原型、自建标签的候选），它们存在图库里，随标注变化重算，删除图库即消失。
- 可以从外部**拉取**公开数据（Danbooru、Bangumi、角色索引）；发出去的只能是文本查询（tag 名、作品名、MD5）。纯文本的结构化或翻译可以接 DeepSeek 这类 API。
- 外网流量超过 500 MB 要先问用户。名字获取和添加角色不设流量预算（用户 2026-10-21 决定，#287）：前者每次只有几 KB，后者在添加按钮上写明预计下载量，确认即是问过。不硬编码猜测的标签名，要查 `tags/tags_v3.csv`。没看过图，不对画面内容下结论。
- **标记类操作一键完成**：不加弹窗，不设必填项，给自动默认值，缺的信息等真正要用时再补（例：原创角色）。
- Photos 只读；图库是索引，不删 Photos 里的图。识别在本机跑（本机识别张数上限已于 2026-10-12 按用户决定删除，#100）。Photos 收录范围和文件夹的 Pixiv / X / 其他出处见 [图库与来源](LIBRARIES.md)，不把 Photos 的来源限制套到所有文件夹上。

## 现阶段路线（用户 2026-11-14 定）

依据是 v0.1.0 发布当天的 [方向调研](DIRECTION_SURVEY_2026-11.md)。产品整理做得深，找图、逛图、用图做得薄，而且只在作者一个人的图库上验证过。按这个顺序走：

1. **0.2.0：让第二个人用得起来**（里程碑 [0.2.0](https://github.com/shio-vinyl/illustash/milestone/1)，发布跟踪 [#444](https://github.com/shio-vinyl/illustash/issues/444)）：2026-11-16 已发布。本地诊断日志、人工结论自动备份是内测的门槛，下一步是小范围内测（#806，排在 0.5）。原定叫 0.1.1，人工结论备份（#441）把图库格式升到 v9，按[发布规则](DEVELOPMENT.md#发布)至少升次版本号，2026-11-15 改叫 0.2.0，后面的版本号顺延一位。
2. **0.3：找和逛**（里程碑 [0.3 找和逛](https://github.com/shio-vinyl/illustash/milestone/2)，总 Issue [#454](https://github.com/shio-vinyl/illustash/issues/454)）：2026-11-18 发布 0.3.0。组合检索与画廊、画面标签中文名、收藏、画师目录、「更多像这张的」、用图动作、后台运行。要用的数据都已经在库里，不需要新模型。
3. **认得更全、找回更多画师**（里程碑 [0.3.1 认得更全与修复](https://github.com/shio-vinyl/illustash/milestone/4)）：2026-11-19 发布 0.3.1，只放了后端修复和识别扩充，由 Codex 做。研究和界面并行，照原顺序推进：自建标签候选接入（#157）暂缓；新角色覆盖（#380）和多人图裁人再认（#456）已关，后者评估后保留整图 CCIP；接下来是画风候选画师（#455）→ 疑似 AI 提示（#184）。推理运行库迁移（#290）最低优先级。
4. **界面整体升级**（里程碑 [0.4 界面整体升级](https://github.com/shio-vinyl/illustash/milestone/5)）：按 #685 的方向整体重做前端，渲染用自写底座，不引框架也不引 Node（#469）。2026-11-19 用户定，原来的 0.4 顺延为 0.5。0.4 之后先发修订版 0.4.1（里程碑 [0.4.1 修复与任务协调](https://github.com/shio-vinyl/illustash/milestone/6)）：修掉现有的 bug，盘点后台任务协调层（#802），2026-11-21 用户定。
5. **跨设备放最后**（里程碑 [0.5 手机访问与准备公开](https://github.com/shio-vinyl/illustash/milestone/3)）：第 0 步是手机浏览器访问（#459），排在 0.4 之后。

分发：内测阶段不花钱；macOS 公证（每年 99 美元）放到准备公开宣传之前再办；Windows 先看 Microsoft Store 加 winget 能不能走通（#443）。公开宣传放在 0.3 之后，先中文社区再英文，素材只用全年龄图。

## 功能

以下编号保留供现有文档引用；已实现的机制链接到现行参考，不在这里重复实施记录。

1. **画廊式偶尔提问（主动学习）**
   - 方向：通过少量人工回答积累角色学习样本与无偏抽查样本，避免打断浏览。
   - 可以改进回答率与提问频率的配合、卡片内查看大图的体验。现行提问、抽查和界面入口以 [WEB_V2.md](WEB_V2.md) 及 [新图库引导](WEB_V2.md#新图库引导2026-10-1296) 为准；试用结果记在 #280。

2. **角色中文名与作品、皮肤的层级**
   - 名字只是显示层，不改变角色身份。中文优先、自动来源与人工名称的选择、搜索及后台更新规则统一见 [名字](TERMS_NAMES.md)。
   - 作品、角色、皮肤的身份关系见 [DATA_MODEL.md](DATA_MODEL.md)，当前浏览入口见 [WEB_V2.md](WEB_V2.md)。
   - 名字获取的真实图库试用与失败记录归 #280。

3. **跨设备识别与远程算力**
   - 保留桌面端为其他设备提供算力的方向；离线结果包并不等于已交付通用远程调度。
   - 第 0 步是手机浏览器访问：桌面端开局域网入口，扫码配对，手机上只逛不改（2026-11-14 定，#459，排在 0.3 之后）。这会让应用第一次监听局域网，安全与配对方案经用户确认后才实施。
   - 「手机传缩略图给桌面算」和现有识别结果包不相容：结果包绑定原文件完整字节的 SHA-256，要先定一种新的输入类型。
   - 现行结果包、校验与恢复契约只在 [RESULT_PACKAGES.md](RESULT_PACKAGES.md) 维护；平台交付与验收边界见 [BACKEND_TASKS.md](BACKEND_TASKS.md)。

4. **收录其他来源**
   - 截屏、B 站、微信等专门来源仍可按需求扩展，需分别考虑来源开关、首次识别和排除规则；截屏不一定是插画。
   - 现有文件夹来源可标为「其他」，添加、移除与出处设置见 [来源管理](LIBRARIES.md#来源管理107)。

5. **溯源模块：找回画师**
   - 定位是帮助找到画师主页与图库里同一画师的图片；没有可靠结果就不显示，不为了填满字段猜画师。
   - 外部请求需要用户授权，候选不等于人工结论。现行任务与授权边界见 [BACKEND_TASKS.md](BACKEND_TASKS.md#溯源生命周期)，研究依据与仍有效的决定见 [PROVENANCE.md](PROVENANCE.md)（特别是第 8、9 节）。
   - 本地 OCR 计算已于 2026-10-05 按用户决定删除（#177）。文件 MD5 与像素哈希是两种方法，旧 MD5 摸底不能否定现行像素哈希路线。
   - 「以图搜图」的边界保留：默认关闭，只处理 X / Pixiv 来源，只发小缩略图；向用户说明发给谁、发多大，结果永久缓存，绝不发给大模型。
   - Pixiv 图只能找回约 6%，缺的是种子来源。画风模型（如 Kaloscope）给出候选画师、再由本地比对确认，是目前唯一查到的新来源，作为研究进行（#455）。它只出候选，不当结论。
   - Pixiv 2026-06 修改了服务条款（禁止机械化批量操作），关注列表与「找 TA 的其他图」的做法按 #442 复核。
   - 不同设备保存文件名的行为需按具体设备验证；不把一次 iOS 样本的结论推广到安卓。画师不在角色的数据模型里（[DATA_MODEL.md](DATA_MODEL.md#8-不在本模型范围内)），由溯源模块和画师词条（[TERMS_ARTISTS.md](TERMS_ARTISTS.md)）负责。

6. **校准过的概率打分**
   - 方向：用积累的人工结论校准候选排序，不能把模型分数直接解释为身份正确率。
   - 现行强弱证据与“可能认错”的规则见 [WEB_V2.md](WEB_V2.md#证据强弱与可能也是-ta2026-09-23)；证据不足时不得为凑校准门槛撤掉机器归属。
   - 身份策略 `v2` 已于 2026-09-30 按用户决定彻底放弃，不再作为待启用模式；现行边界见 [TERMS.md](TERMS.md#5-剩余工作)。

7. **按标签建 Photos 相簿（写回）**
   用户明确说先不做，因为有风险；以后若做，按需求、按标签建相簿，需另行确定写回范围。

8. **原创角色的标记与命名**
   - 保持一键标记，不要求标记时填写画师或名字。界面上原创角色暂时只有共享的“未细分”标记，不新建独立原创角色，见 [原创角色统一标注](WEB_V2.md#更新原创角色统一标注按需细分2026-09-26)；以后怎么细分见 [#695](https://github.com/shio-vinyl/illustash/issues/695)。
   - 改名已使用角色页「⋯ → 编辑资料…」的显示名字段；保存与撤销见 [自建角色的资料](WEB_V2.md#自建角色的资料2026-09-26)。

9. **画廊视图**（已实现，0.3，[#445](https://github.com/shio-vinyl/illustash/issues/445)）
   - 画廊就是「保存的筛选加封面」，存在图库里，随导出带走。现行做法见 [WEB_V2.md](WEB_V2.md#筛选条与画廊2026-11-17445)；进人工结论快照的事记在 [#533](https://github.com/shio-vinyl/illustash/issues/533)。

10. **身份、链接、名字三层数据模型**
    - 身份只认内部 ID，外部 tag 是链接，显示名独立；作品也有身份。模型与操作规则见 [DATA_MODEL.md](DATA_MODEL.md)，核心当前表与投影见 [TERMS_SCHEMA.md](TERMS_SCHEMA.md)。
    - 现有身份策略只支持未设置与 hybrid；人工关系决议保留证据与撤销，不把历史试验的 `v2` 核验锚点库接入现行规则。

11. **收藏与个人偏好排序**
    - 收藏是一种人工标记，一键完成、可撤销、按重复组扩展（2026-11-14 定，0.2 做，#447）。
    - 以后用收藏当正例，在已存的 WD 特征上学一个只属于本图库的偏好打分，用来排首页和画廊。调研里通用审美打分器和单个用户判断的一致率接近随机，所以不用通用打分器。

## 单人规则与吉祥物（2026-09-26）

这些是已定的产品约束，不是待实施清单；核心的现行实现见 [TERMS_CHARACTERS.md](TERMS_CHARACTERS.md)。

- **`1girl+1boy` 规则**：没有多人标签时，第二名以后的弱证据候选只放在“也可能是”；人工确认仍能表达多人。
- **“不算角色，只当标签”**：不计入角色数、单人/多人图人数，也不参与主动提问和角色学习；识别证据保留，可通过标签筛选找到图片，只有这类标签的图不算“未识别”。在单人图和 `1girl+1boy` 图上，只有强证据才挂这类标签。资料库与角色页均有相应操作。
- **默认名单与用户选择**：默认只当标签的名单由 [角色导入核心](../crates/core/src/character_import.rs) 的 `DEFAULT_TAG_KEYS` 维护；用户手动改过的选择不被默认值覆盖。有官方形象的主角不因属于玩家化身就一概降为标签。
- 验证这些规则要覆盖不同用户画像；旧界面留下的否定记录不能单独作为修改默认规则的依据。已删除的评测工具不再作为可运行入口（#186）。

## 移动端与桌面端（2026-09-26 定方向，移动端阶段再做）

- **受众**：国内安卓用户多数不开云相册，图只存在手机本地；X、Pixiv 各自保存到自己的文件夹，来源按文件夹判断。
- **远程算力必做**：安卓的首次全量由手机经局域网把缩略图（约 448 px）传给桌面端，桌面端算完把结果传回。约 5 万张合计约 2–3 GB（估算）。桌面端需要支持 Windows；配对用扫码，不需要账号或服务器。首次全量要考虑国产 ROM 的后台限制，提供常驻通知并提示保持亮屏或插电。
- **iOS（开了 iCloud 照片）**：方向是桌面端读取 Mac 本机 Photos，两端只同步识别结果和人工结论，走用户自己的 iCloud 私有数据库，不传图片。
- **分工**：首次全量和大规模重算交给桌面端；日常增量尽量在手机本机跑，低端设备跑不动时再交给桌面端。
- **资产 ID 与设备链接**：图库内部资产 ID 和 `asset_links` 已存在，见 [LIBRARIES.md](LIBRARIES.md#3-资产-id-和链接)。移动端仍需设计 iOS `PHCloudIdentifier`、Mac Photos UUID、安卓路径与内容哈希之间的设备链接；不能直接把设备 ID 当成跨设备身份。
- 设备能力需实测：手机上的 WD / CCIP 速度与模型体积、Mac 与 iPhone 的稳定哈希是否一致、iCloud“优化存储”下原图不在本机时的读取方式。移动端实现前再决定小模型与按需下载策略。

## 已知的局限与可以改进的地方

- **相似检测**：布局相同的截图可能被判成差分；小插图与空白的差异可能被当成遮挡；部分重叠的长图尚未覆盖。贴纸、涂改与真实内容变化在像素上难以分开。现行规则见 [图片关系判断](WEB_V2.md#图片关系判断2026-09-24)。
- **相似分组的提示**：外观相似只是线索，不承诺同一个角色；外形几乎相同的角色可能超出 CCIP 的区分能力。
- **规模**：现有测量最大只到约 5 万张。已知会先撞墙的是研究任务每次整库复制（#457）、溯源证据包上限 10 万张和每次同步逐图重读标签（#458）。
- **来源搬家**：文件夹图片的 ID 绑在「来源 + 路径」上，搬目录或换电脑后人工结论接不上（#439）。
- **名字与身份的增量**（#38）：名字任务提交前的来源指纹核对，以及 hybrid 决议或新建身份后的身份图重建仍与规模有关。2026-10-15 暂不做方案 C 的决定已被 [2026-10-18 决定](https://github.com/shio-vinyl/illustash/issues/38#issuecomment-6248594998) 替代：单一权威由 #201 的核心 v8 完成；当前模型见 [TERMS_SCHEMA.md](TERMS_SCHEMA.md)，历史测量口径见 #38。
